# ADR-modulo-usuarios-perfiles-grupos-roles-sucursales-api-autenticacion-admin: Autenticación de `panel_admin/` y contrato API para el módulo de Usuarios

**Estado:** Propuesto
**Task relacionado:** TASK-modulo-usuarios-perfiles-grupos-roles-sucursales
**Fecha:** 2026-09-25

## Contexto

Hechos confirmados en `docs/tasks/TASK-modulo-usuarios-perfiles-grupos-roles-sucursales.md` (`## Investigación`) y verificados de nuevo en esta etapa:

- `panel_admin/src/app/core/service/auth.service.ts:15-24,37-56` — el login de `panel_admin/` es **100% mock en memoria**, sin ninguna llamada HTTP real.
- La plantilla trae `panel_admin/src/app/core/interceptor/jwt.interceptor.ts` (JWT), pero el backend **no tiene `simplejwt` ni ninguna librería JWT instalada** (`INSTALLED_APPS`, `praxsa_manager/settings.py:41-56`) — solo `rest_framework.authtoken` (Token auth), ya usado por `proforma/`.
- El único endpoint de login real que expone hoy el backend es `POST /product/api-token-auth/` → `CustomAuthToken` (`product/custom_views/auth_token.py`), que hace `client = Client.objects.get(user_id=user)` **sin manejar el caso de que no exista** — es decir, asume que todo usuario autenticado tiene un registro `Client` (cliente final de `proforma/`). El personal administrativo (staff que gestionaría usuarios/grupos/sucursales desde `panel_admin/`) normalmente **no** tiene un `Client` asociado → este endpoint lanzaría `Client.DoesNotExist` (500) para un login de staff. **No se puede reusar tal cual.**
- `REST_FRAMEWORK['DEFAULT_PERMISSION_CLASSES']` = `['rest_framework.permissions.DjangoModelPermissionsOrAnonReadOnly']` (`settings.py:119-129`) — el proyecto ya delega en permisos estándar de Django (`auth.Permission` por modelo: `add_*`, `change_*`, `delete_*`, `view_*`).
- No existe hoy ningún serializer ni endpoint para `User`, `Group`, `Permission` o `Sucursal` orientado a gestión administrativa (`ls product/serializer/` solo lista `client_serializer.py`, `invoice_serializer.py`, `layer_serializer.py`; `product/urls.py` no expone nada de esto).
- `panel_admin/` no está conectado a ningún `docker-compose*.yml` ni a `nginx/` — no hay despliegue real de este panel todavía.
- `ADR-modulo-usuarios-perfiles-grupos-roles-sucursales-modelo-datos-permisos.md` (este mismo task) ya decidió: `Profile` (1:1 con `User`, solo `phone_number`), "Roles" = `Group`+`Permission` nativos, `Sucursal.empleado` como única fuente de verdad usuario↔sucursal, soft delete = `User.is_active=False`.

Esta decisión cubre: cómo se autentica `panel_admin/` contra `praxsa_manager`, qué endpoints REST nuevos se exponen para el módulo de Usuarios, y qué controla el acceso a ellos.

## Decisión

1. **Autenticación de `panel_admin/`: Token auth de DRF (no JWT)**, consistente con lo que ya usa `proforma/` y con lo único que el backend tiene instalado (`rest_framework.authtoken`). Se adapta `panel_admin/src/app/core/interceptor/jwt.interceptor.ts` para enviar `Authorization: Token <token>` (en vez del esquema `Bearer` que trae la plantilla) y se reemplaza por completo el contenido mock de `core/service/auth.service.ts` por una llamada HTTP real al endpoint nuevo del punto 2. `core/models/user.ts` se extiende con los campos que la UI necesita mostrar (al menos `is_staff`/nombre de grupos, para las decisiones de UI por privilegio que ya definió el DDR de diseño), sin inventar un esquema de rol propio en el frontend — el frontend refleja lo que el backend informa, no decide reglas nuevas.
2. **Nuevo endpoint de login para staff**: `POST /product/admin-token-auth/` (nombre a confirmar en `delivery-plan`), vista nueva basada en `rest_framework.authtoken.views.ObtainAuthToken` (igual que `CustomAuthToken`, pero **sin** la dependencia de `Client`). Devuelve `{token, user_id, username, email, first_name, last_name, is_staff, groups: [nombres]}`. Se restringe con una validación explícita: si `user.is_staff` es `False`, se rechaza el login por este endpoint (403), para que un cliente final de `proforma/` no pueda autenticarse contra el panel administrativo con sus mismas credenciales. `/product/api-token-auth/` (el existente, usado por `proforma/`) **no se toca** — se deja intacto para no arriesgar el flujo de clientes.
3. **Endpoints REST nuevos para el módulo de Usuarios**, todos bajo permisos estándar de Django ya configurados (`DjangoModelPermissionsOrAnonReadOnly` a nivel global, o `DjangoModelPermissions` explícito en cada vista para exigir autenticación siempre, sin el `AnonReadOnly` que no aplica a datos de usuarios):
   - `User` (listar/ver/crear/editar/activar-desactivar) — un `ModelViewSet` o vistas explícitas en `product/custom_views/` (patrón ya usado por `InvoiceView`, `BobinaView`), con un serializer de escritura que:
     - En creación: recibe `username, password, password_confirm, is_active, first_name, last_name, email, phone_number (→ Profile), sucursales (ids → Sucursal.empleado), groups (ids)`; valida `password` contra `AUTH_PASSWORD_VALIDATORS` (`django.contrib.auth.password_validation.validate_password`) y que `password == password_confirm`; crea el `User` con `User.objects.create_user(...)` (hashing estándar de Django, nunca manual); crea el `Profile` asociado; asigna `sucursales` a `Sucursal.empleado` y `groups` a `user.groups`, todo dentro de una transacción atómica (`transaction.atomic`) para que un fallo a mitad de camino no deje un `User` sin `Profile` o sin sus relaciones.
     - "Eliminar" = `PATCH` que setea `is_active=False` (mismo mecanismo que "Desactivar" — ver ADR de modelo de datos, punto 4). No se expone un `DELETE` que borre la fila.
     - "Cambiar contraseña": endpoint separado (p. ej. `POST /product/users/<id>/set-password/`) que reusa `django.contrib.auth.password_validation.validate_password` y `user.set_password(...)` — nunca un hash manual.
   - `Sucursal`: serializer simple + vistas CRUD nuevas (no existía ningún serializer para este modelo).
   - `Group`+`Permission`: vistas para listar/crear/editar `Group` y para asignar/quitar `Permission` de un `Group` (`group.permissions.set(...)`), reusando los modelos nativos de `django.contrib.auth`.
4. **Autorización**: se reusa `DjangoModelPermissions`/`DjangoModelPermissionsOrAnonReadOnly` ya configurado globalmente — es decir, la Fuente de verdad de "quién puede hacer qué" son los `Permission` de Django asignados al usuario (directamente o vía `Group`), exactamente el mecanismo que el requerimiento pide seguir. Adicionalmente, se recomienda (no se decide en detalle aquí, queda para `delivery-plan`) exigir `is_staff=True` como condición mínima para acceder a cualquier endpoint de este módulo, vía una `permission_class` compuesta simple, para que un cliente final autenticado con `/product/api-token-auth/` nunca alcance estos endpoints aunque de alguna forma tuviera un `Permission` asignado por error.
5. **No se reutiliza el patrón de `PublicCatalogThrottle`** (limitado a los endpoints públicos de catálogo, `settings.py:125-128`) — estos endpoints nuevos requieren autenticación siempre, no hay caso de uso anónimo.

## Alternativas consideradas

- **Modificar `CustomAuthToken` para tolerar la ausencia de `Client`** (en vez de crear un endpoint nuevo): descartada. Ese endpoint ya está en producción sirviendo el login de `proforma/`; tocar su lógica para agregar una rama "si no hay Client, no lo busques" mezcla dos audiencias (cliente final vs. staff administrativo) en una sola vista, con más ramas condicionales y más riesgo de romper el flujo existente por un cambio pensado para otro caso de uso. Un endpoint nuevo, aislado, es más simple y no toca nada que ya funciona.
- **Instalar `djangorestframework-simplejwt` para aprovechar el `jwt.interceptor.ts` de la plantilla tal cual**: descartada para este task. `docs/CLAUDE.md:36` pide explícitamente "no agregar dependencias sin avisar antes"; además introduciría un segundo mecanismo de autenticación (JWT) conviviendo con el Token auth que ya usa `proforma/`, sin necesidad real — Token auth ya resuelve el caso de uso (sesión de panel administrativo) sin librerías nuevas. Si en el futuro se decide unificar todo el ecosistema (`proforma/` + `panel_admin/`) bajo JWT, es una decisión más grande que excede este task y debería tener su propio ADR.
- **Exponer `User`/`Group`/`Sucursal` vía el Django admin existente en vez de una API REST nueva**: descartada — el requerimiento pide explícitamente la gestión desde el nuevo panel (`panel_admin/`, Angular), no desde el admin de Django. El admin de Django ya administra estos modelos hoy, pero no es la superficie que se pidió construir.
- **Un solo endpoint "todo en uno" que reciba usuario+perfil+grupos+sucursales en un solo POST atómico (reflejando el wizard de 4 pasos 1:1) vs. separar en varios endpoints por paso**: se decide **un solo POST atómico de creación** (recibe todo el payload del wizard completo, ver punto 3) en vez de 4 llamadas incrementales al backend por cada paso. Justificación: el propio requerimiento dice explícitamente "Antes de crear definitivamente el usuario, mostrar un resumen... Al confirmar: 1. Validar todos los datos nuevamente en backend... 6. Confirmar que la operación se completó correctamente" — describe una sola operación de confirmación al final, no una creación incremental paso a paso. Guardar estado a mitad de camino (p. ej. crear el `User` en el paso 1 y completarlo después) dejaría usuarios a medio crear si el flujo se abandona — el wizard es solo UI/estado de formulario en el frontend hasta la confirmación final.

## Estrategia de rollback / mitigación

- **Autenticación**: el endpoint nuevo (`admin-token-auth`) es aditivo — no reemplaza ni modifica `/product/api-token-auth/` existente. Si falla o tiene un problema de seguridad tras desplegarse, se puede deshabilitar (quitar la ruta de `urls.py`) sin afectar el login de `proforma/`.
- **Endpoints CRUD nuevos**: por defecto exigen autenticación + permiso Django explícito (`DjangoModelPermissions`) — un usuario sin el `Permission` correspondiente no puede usarlos aunque conozca la URL. Mitigación adicional: exigir `is_staff=True` (punto 4) como capa extra ante un error de configuración de permisos.
- **Despliegue**: `panel_admin/` no está en ningún `docker-compose*.yml`/`nginx/` todavía — este ADR no introduce riesgo de producción por sí solo; el riesgo real aparece recién cuando se decida desplegar `panel_admin/` (fuera del alcance de este task, ya señalado como pregunta pendiente en la investigación: "¿reemplaza al Django admin o coexiste?").
- **Migraciones**: ninguna de las decisiones de este ADR requiere migración adicional a la ya decidida en el ADR de modelo de datos (creación de `Profile`) — los endpoints nuevos son código de aplicación (serializers/vistas/urls), no esquema.
- Si se necesita revertir el reemplazo del `jwt.interceptor.ts`/`auth.service.ts` de `panel_admin/` (por ejemplo, se decide sí usar JWT más adelante), es un cambio acotado a esos archivos del frontend — no afecta al backend ni a `proforma/`.

## Consecuencias

- Se gana: un único mecanismo de autenticación (Token auth) para ambos frontends (`proforma/` y `panel_admin/`), sin librerías nuevas; autorización delegada 100% al sistema de permisos nativo de Django, consistente con el resto del backend.
- Se acepta conscientemente: se descarta el interceptor JWT que trae la plantilla comprada tal cual — hay que adaptarlo, no usarlo "de fábrica". Es trabajo adicional pero evita una dependencia nueva y un segundo esquema de auth conviviendo sin necesidad.
- Queda pendiente para `delivery-plan` (deliberadamente, son detalles de implementación, no de arquitectura): nombres exactos de rutas/endpoints, estructura exacta de los serializers, si se usa `ModelViewSet`+`router` o vistas basadas en función (el proyecto ya mezcla ambos estilos hoy — `InvoiceView` es basada en clase, varias vistas de catálogo son basadas en función), y el detalle de qué permisos (`add_user`, `change_user`, etc.) se asignan a qué grupos por defecto.
- Esta decisión no reabre ni contradice `ADR-005-public-catalog-endpoints-protection.md` (endpoints públicos de catálogo, caso completamente distinto) ni `ADR-006-idor-invoice-and-proforma-car-part-info.md` (filtrado de proformas por pertenencia) — son áreas del código no tocadas por este task.
