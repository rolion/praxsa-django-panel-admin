# ADR-modulo-almacen-permisos-rol-frontend: Permisos Django por grupo para `admin`/`almacen`, y `PanelAdminAuthToken` extendido con `groups`/`is_staff` para que el frontend pueda diferenciar rol

**Estado:** Propuesto
**Task relacionado:** TASK-modulo-almacen
**Fecha:** 2026-09-26

## Contexto

El pedido exige dos roles diferenciados (`admin`: CRUD completo sobre Láminas/Bobinas + gestión de Inventario; `almacen`: solo lectura de los tres) validados **en frontend y backend**, reutilizando el sistema de roles/permisos ya implementado, no uno paralelo.

La investigación y el diseño de este task ya dejaron estos hechos confirmados:

- El proyecto usa `django.contrib.auth.models.Group`/`Permission` como mecanismo de rol (no hay modelo `Rol` separado) — ya aplicado en dos módulos reales: Usuarios (`custom_views/user_admin.py`) y Vehículos (`custom_views/vehicle_admin.py`), ambos con el mismo patrón: `_STANDARD_PERMISSIONS = [permissions.IsAuthenticated, IsStaffUser, permissions.DjangoModelPermissions]` para list/create/detail, y `[IsAuthenticated, IsStaffUser]` + `request.user.has_perm('product.change_<modelo>')` explícito para los endpoints de `toggle-active`.
- `permissions.DjangoModelPermissions` de DRF no exige ningún permiso para `GET`/`HEAD`/`OPTIONS` (su `perms_map` por defecto trae lista vacía para esos métodos) — solo exige `add_*`/`change_*`/`delete_*` del modelo para `POST`/`PUT`/`PATCH`/`DELETE`. Esto significa que, con este patrón, cualquier `is_staff` autenticado ya puede leer sin que se le asigne ningún `Permission` explícito, y el bloqueo real de escritura para `almacen` se logra simplemente **no** asignándole `add_window_film`/`change_window_film`/`delete_window_film` (e íd. para `window_film_reel`/`inventario`) al grupo `almacen`.
- Django genera automáticamente los permisos `add_<model>`/`change_<model>`/`delete_<model>`/`view_<model>` para cada modelo — `Window_Film`, `Window_Film_Reel` e `inventario` ya los tienen disponibles sin ninguna migración de permisos nueva.
- **No existe ningún seed/fixture que cree los grupos `admin`/`instalador`/`supervisor`/`caja`** — se crean manualmente vía el admin de Django o vía `/users/groups` (`GroupListCreateView`, ya construido por `TASK-modulo-usuarios`). El grupo `almacen` que pide este requerimiento se crea de la misma forma.
- **Brecha real, confirmada en investigación y diseño**: `PanelAdminAuthToken` (`custom_views/auth_token.py:32-54`), el login real de `panel_admin/`, devuelve `{token, user_id, username, name, lastname}` — sin `groups` ni `is_staff`. El frontend (`core/models/user.ts`, `core/service/auth.service.ts`, `core/guard/auth.guard.ts`) no tiene ningún dato de rol hoy. Ningún módulo anterior (Usuarios, Vehículos) necesitó esto — cualquier `is_staff` podía gestionar todo en ambos. Este es el primer requerimiento que exige diferenciar UI por rol dentro de un mismo módulo, y el DDR de diseño (`docs/design/DDR-modulo-almacen-listado-y-flujo-almacen.md`, sección "Comportamiento por privilegio/estado") dejó esta decisión explícitamente para esta etapa.
- `ADR-modulo-usuarios-perfiles-grupos-roles-sucursales-api-autenticacion-admin.md` (Parcialmente superseded) ya había anticipado este problema en su punto 1 original: "`core/models/user.ts` se extiende con los campos que la UI necesita mostrar (al menos `is_staff`/nombre de grupos)... el frontend refleja lo que el backend informa, no inventa un esquema de rol propio" — pero esa extensión nunca se implementó (el `PanelAdminAuthToken` que reemplazó la propuesta original de ese ADR no la incluyó). Esta decisión la retoma y la concreta.

## Decisión

1. **Backend — permisos de Láminas/Bobinas/Inventario**: mismo patrón exacto que Usuarios/Vehículos.
   - `almacen/laminas`, `almacen/laminas/<pk>/`, `almacen/bobinas`, `almacen/bobinas/<pk>/`: `_STANDARD_PERMISSIONS = [IsAuthenticated, IsStaffUser, DjangoModelPermissions]`.
   - `.../toggle-active/` (Láminas y Bobinas): `[IsAuthenticated, IsStaffUser]` + `request.user.has_perm('product.change_window_film')` / `'product.change_window_film_reel'` explícito, igual que `CarBrandToggleActiveView`/`CarModelToggleActiveView` (`vehicle_admin.py:46-65,151-169`).
   - `almacen/inventario` (`GET`): `[IsAuthenticated, IsStaffUser]` — sin `DjangoModelPermissions` porque `GET` no exige ningún permiso en ese esquema de todos modos; el filtro por sucursal (`Inventario_Business.get_inventario_queryset_by_role`) ya restringe qué ve cada usuario, no si puede ver.
   - `almacen/inventario/<pk>/` (`PATCH`, "gestionar"): `[IsAuthenticated, IsStaffUser]` + `request.user.has_perm('product.change_inventario')` explícito, mismo patrón que los `toggle-active` — un usuario `almacen` sin ese permiso recibe `403`.
2. **Grupo `almacen` se crea manualmente** (vía Django admin o `/users/groups`, ya construido), igual que `admin`/`instalador`/`supervisor`/`caja` hoy — no se agrega ninguna migración de datos que lo cree automáticamente, para no romper la convención ya establecida (0 seeds de grupos en todo el proyecto) ni inventar un mecanismo nuevo solo para este rol. Se le asignan los permisos Django `view_*` (implícito, no necesita asignación real por lo del punto de `GET` sin restricción) — en la práctica, al grupo `almacen` **no se le asigna ningún `Permission` de escritura** sobre `Window_Film`/`Window_Film_Reel`/`inventario`; al grupo `admin` se le asignan `add_window_film`, `change_window_film`, `delete_window_film`, `add_window_film_reel`, `change_window_film_reel`, `delete_window_film_reel`, `change_inventario`. Esta asignación es un paso operativo (vía el panel de Grupos ya existente), no código nuevo.
3. **`product/helper/user.py::User_Helper` gana `is_request_user_almacen`**, simétrico a `is_request_user_supervisor`/`is_request_user_caja` (líneas 16-22), para que cualquier lógica de negocio futura que necesite distinguir el grupo por nombre (no solo por `Permission`) tenga el mismo mecanismo ya usado. No se usa en los endpoints de Almacén en sí (que se apoyan en `DjangoModelPermissions`, no en nombre de grupo), pero mantiene `User_Helper` consistente como el único lugar del proyecto que resuelve "¿qué grupo tiene este usuario?" por nombre.
4. **`PanelAdminAuthToken` se extiende (aditivamente) para incluir `groups` e `is_staff`** en la respuesta de login: `{token, user_id, username, name, lastname, is_staff, groups: [<nombres>]}` (`custom_views/auth_token.py:41-54`). Es un cambio de una línea agregando dos claves al diccionario de respuesta — no cambia ninguna clave existente, no rompe ningún consumidor actual del login (el frontend simplemente ignoraba estos campos porque no existían). Esto cierra la brecha transversal identificada: el frontend ahora sabe, apenas loguea, a qué grupos pertenece el usuario, sin necesitar una llamada adicional.
5. **Frontend — `core/models/user.ts` gana `groups: string[]`** (y opcionalmente `isStaff: boolean`, aunque no se usa todavía en ningún guard). `core/service/auth.service.ts::login()` mapea el campo nuevo del response igual que los demás. Se agrega un método `AuthService.hasGroup(name: string): boolean` (compara contra `currentUserValue.groups`, minúsculas, mismo criterio que `User_Helper.to_lowercase` del backend) — es el único punto del frontend que sabe cómo se determina el rol; los componentes de Almacén (y cualquier módulo futuro) lo consultan en vez de leer `groups` directamente, para no esparcir la lógica de comparación de nombres por toda la UI.
6. **Los componentes de Almacén ocultan Crear/Editar/Eliminar/Gestionar con `*ngIf="authService.hasGroup('admin')"`** (o el getter equivalente), tal como define el DDR de diseño. Esta es la capa de UX — la decisión explícita de este ADR es que **la verificación real es la del punto 1** (backend); si `hasGroup('admin')` tuviera un bug o el usuario manipulara el DOM/localStorage, el backend seguiría rechazando `POST`/`PATCH`/`DELETE` sin el `Permission` correspondiente.
7. **No se toca `AuthGuard`** (`core/guard/auth.guard.ts`): sigue verificando solo que haya sesión (`token`), no rol — el pedido no exige bloquear la *navegación* a `/almacen/laminas/create` para un usuario `almacen` con un guard de ruta (solo que los botones no estén disponibles y que el backend rechace la operación); agregar un guard de permiso por ruta sería una superficie nueva no pedida. Si un usuario `almacen` navega manualmente a esa URL, ve el formulario pero cualquier envío falla con `403` del backend — comportamiento aceptado explícitamente (ver Alternativas).

## Alternativas consideradas

- **No tocar `PanelAdminAuthToken` y resolver el rol en el frontend con una llamada adicional a `GET almacen/...` o a un endpoint `/me` nuevo.** Descartada: introduce una segunda llamada de red en el flujo de login (latencia adicional, y un estado transitorio "logueado pero sin saber el rol todavía") para resolver algo que el propio login ya puede informar sin costo — el `User` de Django ya trae `.groups` resuelto en el mismo request que genera el token. Un endpoint `/me` sería justificado si `groups` cambiara con frecuencia durante una sesión larga (no es el caso: cambiar el grupo de un usuario ya activo no tiene ningún flujo de refresco de sesión en este proyecto) o si se necesitara más información de perfil — no hay esa necesidad hoy.
- **Guard de ruta por permiso** (bloquear la navegación a `/almacen/laminas/create` para `almacen`, no solo ocultar el botón). Descartada por ahora: el pedido dice "no deben estar disponibles en la UI" (botones), no exige bloquear la URL directa, y el backend ya es la barrera real si se navega ahí manualmente y se intenta guardar. Agregar un guard de ruta por permiso sería una superficie de seguridad nueva no pedida por el requerimiento — se puede agregar después como refuerzo de UX si el negocio lo pide, sin que sea parte de esta decisión.
- **Modelo `Rol` nuevo, separado de `Group`/`Permission`.** Descartada — el pedido exige explícitamente reutilizar el sistema de roles ya implementado, y ya existe (`Group`/`Permission` + `DjangoModelPermissions`), consistente con `ADR-modulo-usuarios-perfiles-grupos-roles-sucursales-modelo-datos-permisos.md`, que ya tomó esta misma decisión para todo el proyecto.
- **Que el backend devuelva flags de capacidad ya computados** (ej. `can_manage_almacen: true/false`) en vez de la lista cruda de `groups`. Se consideró porque evita que el frontend tenga que saber el nombre literal `'admin'` — pero se descarta por inconsistencia con el patrón ya elegido en el ADR de Usuarios (punto 1 original: "el frontend refleja lo que el backend informa... al menos `is_staff`/nombre de grupos") y porque devolver `groups` crudos es más general: sirve para *cualquier* decisión de UI futura basada en rol, no solo Almacén, sin tener que agregar un flag nuevo al login por cada capacidad que un módulo futuro necesite distinguir.

## Estrategia de rollback / mitigación

- **Extensión de `PanelAdminAuthToken`**: aditiva pura (agrega claves a un diccionario de respuesta, no quita ni renombra ninguna) — revertirla es quitar 2 líneas, sin ningún efecto en `proforma/` ni en el login de clientes (`CustomAuthToken`, que no se toca). Ningún consumidor actual del login se rompe porque ninguno leía `groups`/`is_staff` (no existían).
- **Permisos nuevos por grupo**: es configuración de datos (asignar `Permission` a un `Group` vía el panel ya existente), no código — si se asigna mal, se corrige desde `/users/groups` sin necesidad de un despliegue nuevo.
- **`User_Helper.is_request_user_almacen`**: función pura nueva, aditiva, sin efecto en el comportamiento de los métodos existentes (`is_request_user_admin`, etc.) — no hay riesgo de regresión en la lógica de negocio que ya usa este helper (filtrado de sucursales en reportes/pagos).
- **`hasGroup()` en el frontend**: si el criterio de comparación de nombre resultara insuficiente (ej. el negocio pide más de un grupo equivalente a "almacen"), es un cambio acotado a un método, sin tocar el contrato del backend.
- Ningún cambio de esta decisión toca autenticación existente de `proforma/` (`CustomAuthToken`, `api-token-auth/`) ni infraestructura — el riesgo es exclusivamente de aplicación, no de despliegue.

## Consecuencias

- Se cierra una brecha transversal (el frontend de `panel_admin/` no sabía el rol del usuario) que afectaba potencialmente a cualquier módulo futuro, no solo a Almacén — Usuarios y Vehículos podrían adoptar `hasGroup()` más adelante si alguna vez necesitan diferenciar UI por rol, sin volver a resolver este problema.
- El backend queda como la única barrera de seguridad real (consistente con el pedido: "no confiar únicamente en ocultar botones en Angular") — la UI oculta botones por comodidad, el `Permission` de Django decide de verdad.
- Se acepta que un usuario `almacen` que navegue manualmente a una URL de creación/edición vea el formulario (sin guard de ruta) — UX subóptima menor, aceptada conscientemente para no construir una superficie de seguridad de frontend no pedida; el envío del formulario falla igual con `403`.
- El grupo `almacen` sigue sin ningún mecanismo de creación automática, igual que los otros 4 grupos del proyecto — sigue siendo un paso manual de configuración por ambiente (dev/stg/prod), documentado explícitamente para que no se asuma que "ya existe" en un ambiente nuevo.
