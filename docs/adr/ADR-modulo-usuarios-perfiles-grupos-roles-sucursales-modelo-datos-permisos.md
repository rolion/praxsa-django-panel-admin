# ADR-modulo-usuarios-perfiles-grupos-roles-sucursales-modelo-datos-permisos: Modelo de datos para Perfil, Roles y relación Usuario↔Sucursal

**Estado:** Propuesto
**Task relacionado:** TASK-modulo-usuarios-perfiles-grupos-roles-sucursales
**Fecha:** 2026-09-25

## Contexto

`docs/tasks/TASK-modulo-usuarios-perfiles-grupos-roles-sucursales.md` (`## Investigación`) estableció los siguientes hechos, base de esta decisión:

- El proyecto usa `django.contrib.auth.models.User` estándar (sin `AUTH_USER_MODEL` custom).
- `Sucursal.empleado` (`product/models.py:105`) ya es un `ManyToManyField(User)` y ya lo consumen 5+ módulos de negocio (`business/inventario.py`, `business/proforma.py`, `business/pago.py`, `business/precio_venta.py`, `business/orden_trabajo.py`, `admin_config/inventory.py`, `product/helper/user.py` indirectamente vía `Sucursal`).
- `Group` de Django **ya se usa como mecanismo de rol** en `product/helper/user.py:4-25` (`User_Helper`), comparando `user.groups.values_list('name', flat=True)` contra literales `'admin'`, `'instalador'`, `'supervisor'`, `'caja'`.
- No existe ningún modelo `Profile` ni `Rol` en `product/models.py` hoy (verificado, sin resultados de `Grep`).
- Existe un modelo `Client` (`product/models.py:89-99`: `name, last_name, phone_number, ci_nit, user_id FK a User`) que es conceptualmente el registro de datos personales del **cliente final** de `proforma/` — no del personal administrativo. Su forma es parecida a lo que el requerimiento pide para "Perfil" (nombre, apellido, teléfono ligados a un `User`), pero su propósito de dominio es distinto (clientes que compran proformas, con `ci_nit`, sin relación a `Sucursal`).
- No existe soft delete en ningún lado del proyecto (`Grep` de `is_deleted|soft_delete|SoftDelete|deleted_at` sin resultados). El único campo de estado ya existente y con semántica equivalente es `User.is_active`, estándar de Django.
- `docs/design/DDR-modulo-usuarios-perfiles-grupos-roles-sucursales-listado-y-flujo-usuarios.md` (etapa de diseño ya completada) asume que "Perfiles" en el menú **no** tiene tabla propia separada de "Usuarios" — se edita como parte del mismo flujo de usuario. Esta decisión de UI no obliga a nada sobre el modelo de datos backend, pero es consistente con tratar `Profile` como una extensión 1:1 de `User`, no como una entidad con su propio ciclo de vida independiente.

Preguntas que esta decisión debe resolver: (1) ¿"Perfil" es un modelo nuevo o se reusa `Client`? (2) ¿"Roles" es un modelo nuevo o es la UI para `Group`+`Permission`? (3) ¿Cómo se reconcilia `Profile.sucursales` (pedido por el requerimiento) con `Sucursal.empleado` (ya existente)? (4) ¿Cómo se implementa "eliminar sin borrado físico"?

## Decisión

1. **Nuevo modelo `Profile`** en `product/models.py`, con relación 1:1 a `User` (`OneToOneField(User, on_delete=models.CASCADE, related_name='profile')`), campos `phone_number` (el resto de los campos del requerimiento — nombre, apellido, correo — ya existen nativamente en `User.first_name`, `User.last_name`, `User.email`, así que **no se duplican** en `Profile`). `Profile` **no** se reusa de `Client`: `Client` es un concepto de dominio distinto (cliente final de `proforma/`, con `ci_nit`, sin necesidad de `Group`/`is_staff`) y mezclar ambos crearía acoplamiento entre el módulo de gestión administrativa y el módulo de clientes que hoy son independientes.
2. **"Roles" no es un modelo nuevo** — es la superficie de UI para administrar `Group` (agrupación) y `Permission` (permisos individuales asignables a un `Group`), ambos ya nativos de `django.contrib.auth`. Esto es exactamente lo que pide el requerimiento ("Role (gestión de roles, permisos que se pueden agregar a los grupos)") leído con precisión: no dice "un usuario tiene un Rol", dice "permisos que se pueden agregar a los grupos" — eso ya es la relación `Group.permissions` (M2M nativa de Django). Se reusa también `product/helper/user.py::User_Helper`, que ya resuelve "rol" por nombre de grupo, en vez de introducir un segundo mecanismo paralelo.
3. **`Sucursal.empleado` sigue siendo la única fuente de verdad** para la relación usuario↔sucursal — no se crea un `Profile.sucursales` M2M paralelo. La pantalla de "Sucursales" en el paso 2 del wizard (selección de sucursales al crear un usuario) escribe/lee directamente `Sucursal.empleado`, reutilizando el campo y el patrón ya consumido por `business/inventario.py`, `business/proforma.py`, `business/pago.py`, `business/precio_venta.py`, `business/orden_trabajo.py`. Esto resuelve explícitamente la pregunta de negocio abierta en `docs/integration-and-backlog.md` sección 6 ("¿`Sucursal.empleado` es la única fuente de verdad...?") para el alcance de este task: sí, se mantiene como la única fuente.
4. **Eliminación (soft delete) = `User.is_active = False`**, la convención estándar de Django (es literalmente el campo que Django usa para "deshabilitar sin borrar" — `AbstractUser.is_active`, ya consultado por `ModelBackend.authenticate()` para rechazar login de usuarios inactivos). No se agrega un campo `is_deleted` custom. Esto también resuelve de forma unívoca la acción "Activar/Desactivar" del requerimiento: es el mismo campo, no dos mecanismos distintos para dos botones distintos.
5. **Migración**: nueva migración de `product` (parte de `0106_proforma_header_status.py`, la última existente) que crea la tabla `Profile` — aditiva, sin tocar ninguna tabla/columna existente. No se migran datos de `Client` a `Profile` (son conceptos distintos, ver punto 1); no se migra `Sucursal.empleado` (no cambia).

## Alternativas consideradas

- **Reusar `Client` como `Profile`** (agregarle `is_staff`-awareness o reusar tal cual): descartada. `Client` ya tiene un significado de dominio específico (cliente que genera proformas, con `ci_nit` obligatorio por `RegexValidator`) consumido por `create_client`/`ClientSerializer` y por el flujo de compra de `proforma/`. Forzar que el personal administrativo también tenga una fila en `Client` sería confuso semánticamente (¿un cajero de sucursal es un "cliente"?) y acoplaría dos módulos que hoy evolucionan independientes. El costo de un modelo `Profile` nuevo (una tabla más, una migración aditiva) es bajo comparado con ese acoplamiento.
- **Modelo `Rol` nuevo, separado de `Group`**: descartada. Sería literalmente un sistema de autorización paralelo al de Django — justo lo que el requerimiento pide evitar explícitamente ("La autenticación, usuarios, grupos y permisos deben seguir, siempre que sea posible, las mismas reglas y conceptos utilizados por Django"). `Group`+`Permission` ya cubren el caso de uso descrito (permisos agrupables, asignables a usuarios via grupo) y ya se usan en la lógica de negocio existente (`User_Helper`). Si más adelante aparece una necesidad real que `Group`/`Permission` no cubran (p. ej. jerarquía de roles, roles con metadata adicional), se puede revisar esta decisión — no se diseña para ese caso hipotético ahora.
- **`Profile.sucursales` M2M nuevo, en paralelo a `Sucursal.empleado`**: descartada. Crearía dos fuentes de verdad para la misma pregunta ("¿a qué sucursal pertenece este usuario?"), con riesgo real de que diverjan (alguien actualiza una y no la otra) — exactamente el patrón de riesgo que `docs/integration-and-backlog.md` sección 2 ya documenta para el cálculo de precios (lógica duplicada en dos lugares). Mantener `Sucursal.empleado` como único punto de verdad es más simple y no rompe nada de lo que ya funciona.
- **Campo `is_deleted` custom en `User`/`Profile` en vez de `is_active`**: descartada. Duplicaría lo que `is_active` ya resuelve nativamente, y el propio requerimiento pide explícitamente reusar las reglas de Django. Además, `is_active=False` ya es respetado por el backend de autenticación de Django (`ModelBackend`) sin código adicional — un `is_deleted` custom exigiría además enseñarle a cada punto de login a chequearlo.

## Estrategia de rollback / mitigación

- **Riesgo bajo**: todo lo decidido aquí es aditivo (tabla `Profile` nueva, sin tocar columnas/tablas existentes; `Sucursal.empleado` no cambia; `Group`/`Permission` no se modifican, solo se exponen en una UI nueva). Ninguna migración existente se edita (regla de `docs/CLAUDE.md:32`).
- `panel_admin/` **no está conectado a ningún `docker-compose*.yml` ni a `nginx/`** (verificado con `Grep` — no aparece en ninguno) — no hay tráfico de producción real dependiendo de este módulo todavía. El "rollback" ante un problema es, en la práctica, no mergear el PR o revertirlo — no hay migración de datos que deshaga ni usuarios reales afectados.
- Si la migración de `Profile` necesitara revertirse ya mergeada, es una migración reversible estándar de Django (`python manage.py migrate product <migración_anterior>`) porque no destruye ni transforma datos existentes, solo agrega una tabla nueva vacía.

## Consecuencias

- Se gana: un solo lugar para "rol" (Group), un solo lugar para "sucursal del usuario" (`Sucursal.empleado`), un solo campo para "activo/inactivo" (`User.is_active`) — sin sistemas paralelos.
- Se acepta conscientemente: `Profile` queda como una tabla chica (solo `phone_number` como campo propio, ya que nombre/apellido/correo viven en `User`) — puede sentirse "vacía" comparada con lo que describe el requerimiento (que lista nombre/apellido/correo/teléfono/sucursales como si fueran todos de `Profile`), pero evitar duplicar campos que `User` ya tiene es más consistente con "reusar Django siempre que sea posible" que replicarlos.
- Queda más difícil (deliberadamente, no es una limitación no vista): si en el futuro un `Client` (cliente final) necesitara convertirse en personal administrativo, no hay conversión automática entre `Client` y `Profile` — habría que crearlo aparte. Se acepta este costo porque son dominios distintos y mezclarlos sería peor.
- Esta decisión no bloquea nada del backlog de `docs/integration-and-backlog.md` — no reabre ni contradice ningún ADR previo (`ADR-002` sobre filtrado por sucursal en reportes sigue usando `Sucursal.empleado` tal cual, sin cambios).
