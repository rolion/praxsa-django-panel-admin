# ADR-modulo-vehiculos-relacion-modelo-item: Reutilizar `Car_Model_Part` como la relación Modelo↔Item, sin crear una tabla de asociación nueva

**Estado:** Propuesto
**Task relacionado:** TASK-modulo-vehiculos
**Fecha:** 2026-09-26

## Contexto

El pedido (punto 12) pide explícitamente no asumir si Modelo↔Item es 1─N o N─N sin revisar el modelo de datos existente. Ya se revisó (`## Investigación` del task): el modelo `Car_Model_Part` (`praxsa_manager/product/models.py:41-55`) ya es la relación Modelo↔Item en producción, y **no es una tabla de asociación genérica**: además de las FK a `Car_Model` y `Car_Part` (esta última `null=True`), tiene campos de negocio propios — `width`, `length` (Decimal), `quantity` (PositiveInteger, default 1), `installation_price` (Decimal) — y ya trae `UniqueConstraint(['car_model_id','car_part_id'], name='unique_model_item')`, que ya impide asociar dos veces el mismo item al mismo modelo (el punto 18 del pedido pide exactamente esto, y ya existe).

Esta relación es **N─N real**: nada impide que el mismo `Car_Part` se use en múltiples `Car_Model` (no hay FK inversa de `Car_Part` a un único modelo), y de hecho `Car_Part` no tiene ninguna referencia a `Car_Model`. Cada fila `Car_Model_Part` representa la configuración de instalación (medidas y precio) de un item específico *en* un modelo específico — el mismo item puede tener configuraciones distintas en modelos distintos.

Verificado además que esta tabla se consulta **en vivo** al crear una proforma, no solo como catálogo de referencia:
- `praxsa_manager/product/serializer/invoice_serializer.py:46-67` — `InvoiceSerializer.validate()` busca `Car_Model_Part.objects.filter(car_model_id=car_model, car_part_id=car_part).first()`; si no existe, **rechaza la creación de la proforma** (`ValidationError`, línea 47-50) con el mensaje "No existe información de precio de instalación para el ítem X en el modelo Y". El precio y subtotal se calculan ahí mismo con `car_model_part.installation_price` (líneas 61-67) y se copian a los datos que van a persistirse.
- `praxsa_manager/product/business/proforma.py:90-92` — valida que el ancho de lámina solicitado sea `>= car_part_item.width` de la fila `Car_Model_Part` correspondiente, en otro flujo de negocio (notas de trabajo).
- Los registros que sí quedan como historial de una proforma ya creada (`Proforma_Detail`, `models.py:237-248`) **copian sus propios valores** de `width`, `length`, `installation_price`, `quantity` al momento de crearse — no tienen FK a `Car_Model_Part`, solo FK directa a `Car_Part` (`models.py:242`). Es decir, `Car_Model_Part` es catálogo de configuración vigente, no un registro histórico perpetuo: modificar o eliminar una fila `Car_Model_Part` no altera proformas ya creadas.

## Decisión

1. **No se crea ninguna tabla de asociación nueva.** El módulo de Vehículos administra la relación Modelo↔Item reutilizando `Car_Model_Part` tal como existe hoy. "Asociar un item a un modelo" desde el panel = crear una fila `Car_Model_Part`. "Quitar un item de un modelo" = eliminar físicamente esa fila `Car_Model_Part` (no es una de las 3 entidades con soft-delete requeridas por el pedido — punto 17 lista Marca/Modelo/Item, no la asociación — y, según lo verificado arriba, borrarla no afecta proformas ya creadas).
2. **El formulario de "agregar item a un modelo" debe capturar `width`, `length`, `quantity` e `installation_price`**, no solo el item a asociar. Esto amplía el alcance descrito en el DDR de diseño (`docs/design/DDR-modulo-vehiculos-listado-y-flujo-vehiculos.md`, que solo contemplaba nombre/selección de item en el modal), porque omitir estos campos crearía una fila `Car_Model_Part` con los defaults del modelo (`width=0`, `length=0`, `installation_price=0`) que la calculadora de precios aceptaría silenciosamente como válida: cualquier proforma nueva para esa combinación modelo-item se facturaría con **$0 de costo de instalación** y sin restricción real de ancho de lámina, un bug de negocio silencioso, no una excepción visible. `delivery-plan` debe reconciliar esto con el DDR (extender el modal, no solo con nombre) antes de planificar el detalle de UI; no hace falta repetir todo el ciclo de `delivery-design`, es una extensión acotada de un formulario ya decidido.
3. **La serializer de asociación debe seguir exponiendo la misma `UniqueConstraint` ya existente** (`unique_model_item`) como validación de negocio explícita (mensaje claro "este item ya está asociado a este modelo"), no solo dejar que la excepción de integridad de base de datos suba sin capturar.
4. **La API de "Modelos" para el detalle expone los items asociados leyendo `Car_Model_Part` con `select_related('car_part_id')`**, mismo patrón que ya usa `product/admin_config/car_model.py:13-23` y `invoice_serializer.py:90` (evitar N+1 queries).

## Alternativas consideradas

- **Crear una tabla de asociación nueva y simple (solo `car_model_id` + `car_part_id`), dejando `Car_Model_Part` como una tabla de "configuración de precios" aparte, poblada después manualmente vía Django Admin.** Se descarta: crearía dos fuentes de verdad para la misma relación (¿un modelo tiene el item asociado si existe en la tabla nueva, si existe en `Car_Model_Part`, o si existe en ambas?), contradice directamente el punto 12 del pedido ("no asumir una relación diferente sin analizar el código existente" — ya se analizó y la relación correcta es `Car_Model_Part`), y no resuelve el problema real: la calculadora de precios seguiría necesitando que alguien complete `Car_Model_Part` en algún momento.
- **Relación M2M simple de Django (`ManyToManyField` sin through model) entre `Car_Model` y `Car_Part`.** Se descarta de inmediato: perdería los campos de precio/medidas que la calculadora ya depende de leer hoy (`invoice_serializer.py:61-67`), rompiendo la creación de proformas.
- **Dejar el modal de "agregar item" solo con nombre/selección de item (como proponía el DDR) y que el precio se complete después, por separado, vía Django Admin.** Se descarta como decisión final porque deja una ventana de bug silencioso de facturación (item asociado con $0 de instalación) entre el momento de asociar desde el panel nuevo y el momento en que alguien se acuerde de completarlo en el Admin — inaceptable para un campo que afecta directamente el cobro al cliente. Se acepta como *fallback* explícito solo si `delivery-plan` decide, con aprobación humana explícita, que el precio se define en una iteración posterior — pero no como el comportamiento por defecto.

## Estrategia de rollback / mitigación

No se requiere ninguna migración de esquema para esta decisión — `Car_Model_Part` ya existe con todos los campos necesarios; la decisión es de comportamiento de la API/UI nueva, no de estructura de datos. Si se detecta que exigir los 4 campos en el formulario de asociación es una fricción excesiva para el negocio, se puede relajar a nivel de serializer (volverlos opcionales con los defaults del modelo) sin ninguna migración ni pérdida de datos — es un cambio reversible de una sola capa. El único riesgo real y ya mitigado es el de "asociación sin precio real"; si de todos modos se decide permitirlo, la mitigación mínima no negociable es que la UI muestre una advertencia visible ("este item no tiene precio de instalación configurado") en el listado de items del modelo, para que no quede oculto.

## Consecuencias

- Se reutiliza 100% el modelo de datos existente, sin nueva migración para la relación en sí — solo se agregan serializers/vistas DRF que hoy no existen para `Car_Model_Part` (fuera del alcance de este ADR puntual, es la capa de API general del módulo).
- El formulario de "agregar item a un modelo" queda más complejo que lo que el DDR de diseño había previsto (4 campos numéricos además de elegir/crear el item) — se acepta conscientemente porque la alternativa es un bug de facturación silencioso.
- Django Admin sigue funcionando exactamente igual sobre estos mismos modelos (no se le hace ningún cambio) — el panel nuevo y el Admin son dos superficies sobre la misma tabla, lo cual ya es el patrón existente del proyecto (todas las entidades gestionadas hoy por Admin seguirán siéndolo en paralelo salvo que se decida lo contrario a futuro).
- Queda abierta y explícitamente fuera de este ADR la pregunta de si el negocio quiere que el panel permita *editar* `width`/`length`/`installation_price` de una asociación ya creada desde la pantalla de detalle del Modelo (el pedido solo describe "agregar item", no "editar item asociado") — `delivery-plan` debe confirmarlo o dejarlo fuera del alcance de esta tarea.
