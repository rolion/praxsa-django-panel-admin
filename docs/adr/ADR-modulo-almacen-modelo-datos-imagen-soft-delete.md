# ADR-modulo-almacen-modelo-datos-imagen-soft-delete: Campos nuevos en `Window_Film`/`Window_Film_Reel`, imagen vía `MEDIA_ROOT` existente, contrato API bajo `almacen/`

**Estado:** Propuesto (ver "Actualización" — CRUD completo de Inventario; ver también corrección de `nro_lote` más abajo)
**Task relacionado:** TASK-modulo-almacen
**Fecha:** 2026-09-26

## Actualización (2026-09-26, Inventario gana Ver/Crear/Eliminar)

La verificación manual del task (usuario real, grupos `admin`+`almacen`) confirmó que el negocio necesita CRUD completo de Inventario, no solo "Gestionar" (ver `docs/design/DDR-modulo-almacen-listado-y-flujo-almacen.md`, sección "Actualización"). Esta sección decide lo que esa actualización de diseño dejó pendiente: mecanismo de eliminación y campos de creación. El resto de este ADR (Lámina/Bobina, imagen, contrato de esos dos modelos) sigue vigente sin cambios.

**Diferencia importante de `inventario` respecto de `Window_Film`/`Window_Film_Reel`**: estos dos son catálogo relativamente estático, solo consumido por el admin panel y por selectors. `inventario`, en cambio, es consumido activamente por lógica de negocio real de ventas/instalación (`business/inventario.py::Inventario_Business` — `reduce_inventory`, `get_bobina_by_sucursal_lamina_width`, `get_inventory_by_sucursal`, etc., todos usados en el flujo de generación de proformas). Copiar el mismo soft-delete sin más (ocultar del panel pero dejar que la lógica de negocio lo siga usando para vender/instalar) generaría una inconsistencia real: el admin creería haber "eliminado" una fila con stock, pero el sistema seguiría vendiéndola.

**Decisión 1 — soft-delete de `inventario` con protección de integridad real (no solo visual)**:
1. Se agrega `is_active = models.BooleanField(default=True, verbose_name="Activo")` a `inventario` — mismo nombre de campo que `Window_Film`/`Window_Film_Reel`, por consistencia de convención en todo el módulo Almacén.
2. **"Eliminar" (`PATCH .../toggle-active/`) solo se permite cuando `to_install == 0`** (sin metros disponibles para instalar) — se rechaza con `400` en cualquier otro caso, con un mensaje explícito ("No se puede eliminar un inventario con metros disponibles para instalar."). Esta restricción es la que hace que el soft-delete sea seguro **sin tocar `Inventario_Business`**: cada método de negocio que decide qué fila de inventario usar para vender/instalar ya filtra `to_install__gt=0` o `to_install__gte=<algo positivo>` (confirmado en `business/inventario.py:33,57,87,93,132` — `get_inventory_by_sucursal`, `reduce_inventory`, `is_window_film_available`, etc.) — es decir, una fila con `to_install == 0` **ya es invisible para toda la lógica de venta/instalación real**, con o sin `is_active`. Restringir la eliminación a ese caso garantiza que "eliminar" nunca oculta stock que el sistema todavía pudiera vender, sin necesitar auditar ni modificar ninguna de esas consultas de negocio ya probadas y sensibles.
3. El listado (`GET almacen/inventario`) sigue el mismo patrón que Lámina/Bobina: filtra `is_active=True` por defecto, `?include_inactive=true` para verlas todas.
4. **Sin protección adicional más allá de la del punto 2** (p. ej. no se bloquea eliminar una fila ya referenciada por un `Proforma_Detail` histórico) — una vez que `to_install == 0`, esa fila ya cumplió su ciclo de venta/instalación; ocultarla del listado por defecto no afecta ningún dato histórico (`Proforma_Detail.inventario` sigue apuntando a la fila, que sigue existiendo en la base de datos, solo con `is_active=False`).

**Decisión 2 — campos de creación manual (`POST almacen/inventario`)**:

| Campo | En el formulario | Justificación |
|---|---|---|
| `sucursal` | Obligatorio (select) | No tiene default razonable; toda fila de inventario pertenece a una sucursal. |
| `bobina` | Obligatorio (select, solo bobinas `is_active=True`) | Mismo criterio que los demás selectores del módulo — no ofrecer bobinas ya eliminadas. |
| `quantity` | Obligatorio | Sin default en el modelo (`PositiveIntegerField` sin `default`); es un dato real del lote que se está dando de alta. |
| `to_install` | Obligatorio | Es el dato central de una alta manual de inventario — "cuánto stock estoy agregando". Un alta con `to_install=0` no tendría sentido de negocio. |
| `precio_compra_mtr_lineal` | Obligatorio | Alimenta el cálculo de utilidad (`Reporte Utilidades`, `admin_config/report_utilidad.py`) — dejarlo en blanco rompería ese reporte para esta fila. |
| `precio_venta_mtr_lineal` | Obligatorio | Alimenta el precio que paga el cliente (`views.py::get_inventory`, fallback de `precio_venta_sucursal`) — mismo motivo que el anterior. |
| `installed` | Opcional, default `0` (servidor) | Un lote recién dado de alta no tiene nada instalado todavía. |
| `original_length` | Opcional, default `= to_install` (servidor) | Semántica del campo es "longitud inicial antes de instalar nada" — si `installed` arranca en 0, es razonablemente igual a `to_install` al momento de la alta. Si el admin conoce un valor distinto (p. ej. ya se instaló algo de este lote antes de registrarlo en el panel), puede pisarlo. |
| `date` | Opcional, default `timezone.now()` (servidor) | Mismo criterio que otros modelos del proyecto con `auto_now_add`-like semantics; el admin puede indicar una fecha distinta si el lote corresponde a un ingreso pasado. |
| `numero_referencia` | Opcional, default `0` (modelo) | Ya tiene default en el modelo; no hay evidencia de que sea un dato crítico para la alta manual. |
| `nro_lote` | ~~Opcional~~ **Obligatorio** (ver corrección abajo) | El panel anterior ya lo trataba como obligatorio en la práctica de negocio, pese a que el modelo lo declara `null=True` — corregido tras feedback directo del usuario durante la revisión del PR (`REV-2026-09-27-modulo-almacen-01`). |

## Corrección (2026-09-27, tras REV-2026-09-27-modulo-almacen-01): `nro_lote` es obligatorio, y el frontend debe replicar las reglas del modelo

`REV-2026-09-27-modulo-almacen-01` encontró que `InventarioCreateSerializer` redeclaraba `nro_lote`/`numero_referencia` sin los `validators`/`max_length` del modelo, permitiendo que un valor inválido pasara la validación del serializer y recién fallara al guardar con una excepción de base de datos no controlada. Al reportar ese hallazgo, el usuario aportó dos correcciones de negocio que no estaban en la decisión original de este ADR:

1. **`nro_lote` es obligatorio, no opcional** — el panel de administración anterior ("panel viejo") ya lo exigía en la práctica, aunque el modelo Django lo declare `null=True` (ese `null=True` histórico no refleja la regla de negocio real). Se corrige la tabla de "Decisión 2" arriba: `nro_lote` pasa a la lista de campos obligatorios del formulario de creación, con el mismo criterio que `sucursal`/`bobina`/`quantity`/`to_install`/precios.
2. **El frontend debe replicar las reglas de validación que el modelo ya define en el backend** — no solo confiar en que el backend rechace un valor inválido después de que el usuario ya llenó el formulario. Esto aplica en particular a `nro_lote` (alfanumérico, `RegexValidator(r'^[0-9a-zA-Z]*$')`, `max_length=15`) pero es un principio general para cualquier campo del formulario de creación/edición de Inventario que tenga una regla de negocio ya codificada en `models.py` — el frontend no debe limitarse a `Validators.required`, debe espejar el patrón/longitud/rango que el modelo exige, para que el usuario vea el error antes de enviar el formulario, no después de un rechazo del servidor (y, en el caso de `numero_referencia`, no depender únicamente de la validación del backend para el límite de `MaxValueValidator(9999999999)`).

**Decisión**: `nro_lote` pasa a obligatorio en `InventarioCreateSerializer` (con los mismos `validators`/`max_length` que el modelo, no una redeclaración plana) y en el formulario de Angular (`Validators.required` + `Validators.pattern(/^[0-9a-zA-Z]*$/)` + `Validators.maxLength(15)`, con el atributo `maxlength="15"` en el `<input>`). `numero_referencia` no cambia su obligatoriedad (sigue opcional, con default `0` del modelo, tal como confirmó el usuario — "ese es valor por defecto"), pero su serializer debe recuperar el `MaxValueValidator(9999999999)` que también se había perdido, y el detalle de implementación (`delivery-plan`/`delivery-engineer`) debe decidir si también espeja ese límite en el frontend (dado que ya no es obligatorio, el riesgo de UX es menor, pero la regla de negocio sigue existiendo).

**Contrato API actualizado**:
- `POST almacen/inventario` (nuevo) — mismo `_STANDARD_PERMISSIONS` (`IsStaffUser` + `DjangoModelPermissions`, exige `add_inventario`) que el resto del módulo. `InventarioListView` pasa de `ListAPIView` a `ListCreateAPIView`, con `InventarioCreateSerializer` nuevo (los campos de la tabla de arriba) para `POST` e `InventarioSerializer` (ya existente) para `GET` — mismo patrón que `UserListCreateView`/`WindowFilmListCreateView` (serializer distinto según el método).
- `GET almacen/inventario/<pk>/` (ya existía, sirve tanto "Ver" como para precargar "Gestionar") — sin cambios, sigue en `InventarioUpdateView`.
- `PATCH almacen/inventario/<pk>/toggle-active/` (nuevo) — mismo patrón que Lámina/Bobina (`[IsStaffUser]` + `has_perm('product.change_inventario')` explícito, **no** `delete_inventario`: se mantiene la misma convención que ya usan los demás `toggle-active` del proyecto, que verifican el permiso `change_*` porque técnicamente la operación es un `PATCH` sobre un campo de estado, no un `DELETE` HTTP — ver `CarBrandToggleActiveView`/`WindowFilmToggleActiveView`). Esto tiene una consecuencia operativa favorable: el grupo `admin` ya tiene `change_inventario` asignado desde la decisión original de este módulo (`ADR-modulo-almacen-permisos-rol-frontend`), así que no hace falta ninguna reconfiguración de permisos para poder "eliminar" — sí hace falta agregar `add_inventario` para poder crear (ver Consecuencias).

## Contexto

La investigación y el diseño de este task ya establecieron que Láminas (`Window_Film`), Bobinas (`Window_Film_Reel`) e Inventario (`inventario`) son modelos de dominio existentes (`praxsa_manager/product/models.py:57-65,67-80,131-144`) sin ningún CRUD administrativo, imagen ni soft delete hoy — solo Django admin y un par de endpoints públicos de solo lectura para `proforma/` (`bobina/<pk>`, `layer/<layer_id>`, `product/urls.py:48-49`).

`TASK-modulo-vehiculos` (PR #48, mergeado a `master` justo antes de esta investigación) resolvió el mismo problema — imagen + soft delete + CRUD — para otro conjunto de modelos de catálogo (`Car_Brand`/`Car_Model`/`Car_Part`), dejando dos ADR ya vigentes que esta decisión adopta directamente en vez de re-evaluar desde cero:

- `ADR-modulo-vehiculos-almacenamiento-imagenes.md`: `MEDIA_URL`/`MEDIA_ROOT` ya configurados (`settings.py:211-212`), `ImageField` con validación Pillow (tipo real del archivo, no extensión) y límite de 5 MB, reemplazo de imagen borrando el archivo anterior del filesystem. `Pillow==10.0.1` ya está instalado (`requirements-3.8.10.txt:21`) — sin dependencia nueva.
- `ADR-modulo-vehiculos-soft-delete.md`: campo `is_active` (no el `is_delete` decorativo de `Proforma_Header`, que nunca filtra ninguna query real), filtrado por defecto en `get_queryset()` con `?include_inactive=true`, "eliminar" = `PATCH` a un endpoint dedicado `.../toggle-active/`, sin cascada automática, selectores de creación/edición restringidos a `is_active=True`.

Esta decisión aplica exactamente esos dos patrones a Láminas y Bobinas, y decide qué hacer con Inventario (que no pidió imagen ni soft delete, pero sí "gestionar/actualizar").

## Decisión

1. **`Window_Film` (Lámina) gana dos campos**: `image = models.ImageField(upload_to='window_films/', null=True, blank=True, verbose_name="Imagen")` e `is_active = models.BooleanField(default=True, verbose_name="Activo")`. Migración nueva y aditiva, partiendo de `0108_car_brand_is_active_car_model_image_and_more.py` (última real tras el rebase de esta rama).
2. **`Window_Film_Reel` (Bobina) gana**: `is_active = models.BooleanField(default=True, verbose_name="Activo")`. Sin imagen — el pedido no la exige para Bobina, y no hay ninguna necesidad de negocio identificada en la investigación que la justifique (evitar sobreingeniería).
3. ~~`inventario` no gana ningún campo de estado ni soft delete.~~ **Superseded por la sección "Actualización" arriba**: el negocio confirmó que sí necesita eliminar filas de Inventario — `inventario` gana `is_active` con la misma protección de integridad descrita ahí (`to_install == 0` como condición para eliminar).
4. **Validación de imagen**: reutilizar literalmente `validate_car_model_image` (`serializer/vehicle_serializer.py:54-68`) — misma función, mismos límites (5 MB, JPEG/PNG/WEBP verificados con Pillow) — extraída a un módulo compartido (`serializer/image_validation.py` o similar) para no duplicar la lógica entre `vehicle_serializer.py` y el serializer nuevo de Almacén. Es la primera vez que dos módulos necesitan la misma validación; extraerla ahora evita que una tercera implementación futura tenga que elegir entre copiar de nuevo o refactorizar retroactivamente.
5. **Reemplazo/borrado de imagen**: mismo mecanismo que `CarModelSerializer.update()` (`vehicle_serializer.py:104-109`) — si el `PATCH` trae una imagen nueva o `null`, borrar el archivo anterior del filesystem (`instance.image.delete(save=False)`) antes de asignar el nuevo valor.
6. **`is_active` de solo lectura en los serializers** (no un campo escribible del `ModelSerializer` estándar) — replica explícitamente la corrección de `REV-2026-09-26-modulo-vehiculos-01` (`serializer/vehicle_serializer.py:14-25`): un `ModelSerializer` sin `read_only=True` en `is_active` interpreta un `multipart/form-data` sin ese campo como `False` (por cómo DRF resuelve checkboxes HTML), dejando una Lámina/Bobina creada desde el panel real (que siempre manda `FormData` por la imagen) inactiva e invisible al instante. "Eliminar"/"activar" solo pasa por el endpoint `toggle-active` dedicado, nunca por `create`/`update` normal.
7. **Contrato API nuevo bajo el prefijo `almacen/`** (no `laminas/`/`bobinas/` sueltos, para que quede agrupado y no colisione con nada existente):
   - `GET/POST almacen/laminas`, `GET/PATCH almacen/laminas/<pk>/`, `PATCH almacen/laminas/<pk>/toggle-active/`.
   - `GET/POST almacen/bobinas`, `GET/PATCH almacen/bobinas/<pk>/`, `PATCH almacen/bobinas/<pk>/toggle-active/`.
   - `GET/POST almacen/inventario`, `GET/PATCH almacen/inventario/<pk>/`, `PATCH almacen/inventario/<pk>/toggle-active/` (ver punto 8 y la sección "Actualización" arriba — `POST` y `toggle-active` se agregaron en la ampliación de alcance).
   Se evita deliberadamente reutilizar las rutas públicas ya existentes `bobina/<int:pk>` y `layer/<int:layer_id>` (`product/urls.py:48-49`) — tienen otro propósito (catálogo público de `proforma/`, permisos `IsAuthenticated` simple sin `IsStaffUser`) y no deben mezclarse con el CRUD administrativo nuevo.
   - Serializers nuevos en un archivo agrupador `serializer/almacen_serializer.py` (mismo criterio que `vehicle_serializer.py`, que agrupa `Car_Brand`/`Car_Model`/`Car_Part`), en vez de reutilizar el `layer_serializer.py` existente (vacío, sin ningún import en el resto del proyecto verificado por `Grep`) — un archivo nuevo con nombre de módulo es más consistente con el patrón ya usado que resucitar un archivo huérfano nombrado por un solo modelo. `layer_serializer.py` queda sin tocar (fuera de alcance: borrarlo no es necesario para esta funcionalidad, ver `docs/CLAUDE.md:31`, "cambios pequeños, un objetivo por cambio").
8. **"Gestionar/actualizar Inventario" (edición) tiene alcance acotado**: el `PATCH almacen/inventario/<pk>/` solo permite modificar `to_install`, `installed`, `precio_compra_mtr_lineal`, `precio_venta_mtr_lineal` y `nro_lote` sobre una fila ya existente — nunca `quantity`, `original_length`, `date`, `sucursal` ni `bobina` (esos campos los fija la lógica de negocio al crear/reducir inventario, `Inventario_Business`, y editarlos desde el panel rompería la trazabilidad de instalaciones ya realizadas). Esta restricción de **edición** sigue vigente sin cambios; lo que se amplió fue la posibilidad de **crear** una fila nueva y **eliminar** una existente — ver sección "Actualización" arriba para el detalle de campos de creación y el mecanismo de eliminación.
9. **Filtro por sucursal en el listado de Inventario**: el `GET almacen/inventario` reutiliza el criterio de negocio ya implementado en `Inventario_Business.get_inventario_queryset_by_role` (`business/inventario.py:14-27`) — un usuario ve solo el inventario de su/s sucursal/es salvo que sea `admin` (`User_Helper.can_view_all_sucursales`). Se adapta la firma para devolver un queryset vacío en vez de `None` cuando el usuario no tiene sucursal asignada (el método actual devuelve `None` en ese caso, pensado para el admin de Django que lo maneja distinto) — detalle de implementación para `delivery-plan`, no cambia la decisión de reutilizar la lógica.
10. **Bobina soft-delete no hereda la protección de integridad del borrado físico**: `WindowFilmReel.delete_model`/`delete_queryset` (`admin_config/window_film_reel.py:25-47`) hoy bloquea el `DELETE` físico si la bobina está referenciada por algún `inventario`. El `toggle-active` nuevo (soft delete) **no replica ese bloqueo**: desactivar una Bobina no borra ni desvincula ninguna fila de `inventario` existente (mismo principio "sin cascada automática" de `ADR-modulo-vehiculos-soft-delete.md` punto 5) — el inventario ya generado sigue intacto y consultable; lo único que cambia es que la Bobina deja de aparecer en el selector de "nueva bobina" y en el listado por defecto. No hay riesgo de integridad porque, a diferencia del `DELETE` físico, el soft delete nunca toca la fila ni la FK.

## Alternativas consideradas

- **Reutilizar `layer_serializer.py` (vacío) para el serializer de Lámina.** Descartada: agrupar los 3 modelos de Almacén en un solo archivo (`almacen_serializer.py`) es más consistente con `vehicle_serializer.py` (que agrupa 3 modelos relacionados) que resucitar un archivo nombrado por un solo modelo sin ningún uso previo.
- ~~Agregar soft delete a `inventario`.~~ **Descartada originalmente, luego revertida** (ver "Actualización"): el negocio confirmó la necesidad real tras la verificación manual.
- ~~Permitir `POST` de alta manual de Inventario.~~ **Descartada originalmente, luego revertida** (ver "Actualización"): mismo motivo. El riesgo de datos inconsistentes que motivó el descarte original se mitiga acotando los campos obligatorios (tabla en "Actualización") y dejando defaults del servidor para los campos que antes solo fijaba `Inventario_Business`.
- **(Actualización) Permitir eliminar cualquier fila de Inventario, sin restricción de `to_install`.** Descartada: haría que "eliminar" desde el panel pudiera ocultar (para el admin) una fila que la lógica de negocio de ventas todavía sigue usando para vender/instalar, generando una discrepancia real entre lo que el panel muestra y lo que el sistema realmente vende. Exigir `to_install == 0` para eliminar es gratis en términos de riesgo, porque esas filas ya son invisibles para `Inventario_Business` de todos modos.
- **(Actualización) Propagar el filtro `is_active` a `Inventario_Business`** (para que una fila "eliminada" quede excluida de la lógica de venta incluso si tuviera `to_install > 0`). Descartada por alcance: tocaría código de negocio sensible y ya probado (usado en el flujo real de generación de proformas), sin que el requerimiento lo pida — la restricción del punto 2 de "Actualización" (`to_install == 0`) ya vuelve este escenario imposible por construcción, sin necesidad de tocar esa lógica.
- **Replicar el bloqueo de integridad Bobina↔Inventario del borrado físico en el soft-delete.** Descartada (ver punto 10): esa protección existe para un `DELETE` real, que sí puede romper una FK; el soft-delete no toca la FK, así que la protección no tiene nada que prevenir en este caso — agregarla sería una regla sin motivo real, y además le impediría a un admin desactivar una Bobina descontinuada que todavía tiene stock histórico, un caso de uso legítimo.
- **Storage de imagen distinto al ya decidido en `ADR-modulo-vehiculos-almacenamiento-imagenes.md`** (nube, base de datos, etc.): no se reconsidera — el pedido exige explícitamente reutilizar la estrategia ya usada por el proyecto, y ya existe una funcionando y recién probada.

## Estrategia de rollback / mitigación

- **Migraciones de `Window_Film.image`/`Window_Film.is_active`/`Window_Film_Reel.is_active`**: aditivas y reversibles sin pérdida de datos (agregan columnas nullable/con default; revertirlas solo las elimina, sin tocar filas existentes de forma destructiva más allá de perder la referencia a la imagen, que seguiría en el filesystem hasta una limpieza manual — mismo perfil de riesgo que `ADR-modulo-vehiculos-almacenamiento-imagenes.md` ya documentó y mitigó para `Car_Model.image`).
- **Infraestructura de imágenes**: no hay cambio nuevo de infraestructura en esta decisión — `MEDIA_ROOT`/`MEDIA_URL`, el volumen Docker y el bloque `nginx /media/` ya fueron decididos y (se asume, no re-verificado en detalle en esta etapa) aplicados por `TASK-modulo-vehiculos`. Si no estuvieran desplegados todavía en algún ambiente, es un riesgo preexistente de ese task, no uno nuevo introducido aquí.
- **Endpoints nuevos bajo `almacen/`**: aditivos puros, no modifican ni reemplazan ninguna ruta existente (`bobina/<pk>`, `layer/<layer_id>` quedan intactos). Si algo falla, se puede quitar la ruta nueva de `urls.py` sin afectar el catálogo público de `proforma/`.
- **Alcance acotado de "Gestionar Inventario" (punto 8)**: si el negocio confirma después que necesita editar más campos, es una ampliación de la lista de campos permitidos en el serializer — un cambio de una línea, no una migración ni un cambio de contrato.
- **Migración de `inventario.is_active`** (Actualización): aditiva y reversible sin pérdida de datos, mismo perfil que las de Lámina/Bobina.
- **Restricción `to_install == 0` para eliminar** (Actualización): si resultara demasiado estricta en la práctica (el negocio quiere eliminar una fila con stock residual por otro motivo, p. ej. un lote dañado), es un cambio de una condición en la vista, no un cambio de contrato ni de modelo.

## Consecuencias

- Láminas y Bobinas quedan con el mismo nivel de funcionalidad que Marca/Modelo/Item (imagen donde aplica, soft delete real, permisos Django) — tercer módulo consecutivo que sigue este patrón, reforzando que es la convención real del proyecto para catálogos administrados desde `panel_admin/`.
- Se acepta conscientemente que el proyecto sigue sin una única fuente de verdad para "estado/borrado" (ahora hay `is_delete` decorativo de Proforma, `is_active` de User, borrado físico de Group/Sucursal, e `is_active` de Vehículos e Inventario-Almacén) — no es responsabilidad de este ADR unificarlo, ya señalado como deuda conocida en `ADR-modulo-vehiculos-soft-delete.md`.
- Inventario queda con una superficie de **edición** deliberadamente angosta (sin cambios en esta actualización) pero ahora con CRUD completo (Ver/Crear/Eliminar) al mismo nivel que Lámina/Bobina — la restricción de campos editables en "Gestionar" y la restricción de eliminar solo con `to_install == 0` son las dos barandas que evitan que ese CRUD nuevo introduzca inconsistencias con `Inventario_Business`.
- **(Actualización)** Requiere un paso operativo nuevo: asignar `add_inventario` al grupo `admin` en cada ambiente (no automatizado, mismo criterio que el resto de permisos de este módulo) — `change_inventario` ya estaba asignado desde la decisión original y cubre tanto "Gestionar" como "Eliminar" (mismo permiso, ver contrato API actualizado).
- La extracción de `validate_car_model_image` a un módulo compartido es el primer caso de reutilización de código entre módulos de catálogo del panel — sienta el precedente de que un tercer módulo futuro con imagen no debería volver a copiar la función, sino usar la compartida.
